\section{Introducción}
El presente proyecto aborda la necesidad de una empresa de combustibles de centralizar la gestión de precios y operaciones de sus distribuidoras. La solución implementada consiste en un sistema distribuido que permite a la empresa matriz definir precios de manera remota, mientras que cada distribuidora puede operar de forma autónoma, incluso en caso de pérdida de conexión. El sistema se compone de tres capas principales: la empresa, las distribuidoras y los surtidores de combustible, cada una con sus propias aplicaciones y responsabilidades.

\section{Diseño de la Arquitectura}
La arquitectura del sistema se divide en tres niveles, siguiendo el modelo propuesto en los requerimientos del proyecto.

\subsection{Nivel 1: Surtidores}
Este nivel está representado por el `surtidor-simulator`, una aplicación en Go que simula el comportamiento de los surtidores de combustible. Cada surtidor se conecta a su distribuidora asignada a través de un socket TCP y envía periódicamente información sobre las ventas realizadas. Los surtidores pueden ser pausados o reanudados de forma remota por la distribuidora.

\subsection{Nivel 2: Distribuidoras}
El backend de la distribuidora, desarrollado en Go, es el núcleo de este nivel. Actúa como servidor para los surtidores, recibiendo y procesando los datos de las ventas. Cada distribuidora tiene su propia base de datos PostgreSQL para almacenar las transacciones. Además, expone una API REST para la interfaz de usuario (`distribuidor-ui`), que permite monitorear las ventas y el estado de los surtidores.

\subsection{Nivel 3: Empresa}
La empresa cuenta con una aplicación backend (`empresa`) y una interfaz de usuario (`empresa-ui`). El backend, aunque actualmente es un prototipo, está diseñado para comunicarse con las distribuidoras, obtener reportes y gestionar los precios de manera centralizada. La interfaz de usuario permite a la empresa monitorear el estado de las diferentes distribuidoras.

\subsection{Comunicación entre Capas}
La comunicación entre los surtidores y las distribuidoras se realiza a través de sockets TCP, utilizando un protocolo de mensajería simple basado en texto. La comunicación entre la empresa y las distribuidoras se realiza a través de API REST, lo que facilita la integración y el intercambio de datos en formato JSON.

\section{Configuración}
Para ejecutar la solución, es necesario contar con Docker y Docker Compose. El archivo `docker-compose.yml` orquesta el despliegue de todos los servicios, incluyendo las bases de datos. Cada servicio se configura a través de variables de entorno definidas en el mismo archivo, como las credenciales de la base de datos, los puertos de red y los identificadores de las distribuidoras.

\section{Experimentación}
Se proponen los siguientes escenarios de prueba:

\subsection{Actualización de precios de combustibles}
La empresa podría enviar una solicitud de actualización de precios a una distribuidora. Se debería verificar que la distribuidora actualiza su factor de utilidad y que los nuevos precios se aplican a las ventas futuras. Esto se puede probar con surtidores disponibles y ocupados (pausados).

\subsection{Generación de reportes}
La empresa solicita un reporte de ventas a una distribuidora. Se debe comprobar que la distribuidora recopila la información de su base de datos y la envía a la empresa en el formato esperado.

\subsection{Pérdida de conexión}
Se puede simular una pérdida de conexión entre una distribuidora y la empresa (por ejemplo, deteniendo el contenedor de la empresa). La distribuidora debe seguir operando y almacenando las ventas localmente. Al restablecer la conexión, se debería sincronizar la información.

\section{Análisis de los resultados}
\subsection{Bondades}
\begin{itemize}
    \item \textbf{Autonomía de las distribuidoras:} La arquitectura permite que cada distribuidora opere de forma independiente, lo que aumenta la resiliencia del sistema.
    \item \textbf{Escalabilidad:} El uso de contenedores facilita el despliegue de nuevas distribuidoras.
    \item \textbf{Flexibilidad tecnológica:} La elección de Go para el backend y React para el frontend demuestra la viabilidad de utilizar diferentes tecnologías en las distintas capas del sistema.
\end{itemize}

\subsection{Debilidades}
\begin{itemize}
    \item \textbf{Backend de la empresa incompleto:} El servicio de la empresa es actualmente un prototipo y carece de la lógica de negocio para la gestión de precios y reportes.
    \item \textbf{Seguridad:} La comunicación entre los componentes no está cifrada, lo que representa un riesgo de seguridad.
    \item \textbf{Sincronización de datos:} El mecanismo de sincronización de datos tras una pérdida de conexión no está completamente implementado.
\end{itemize}

\section{Conclusiones}
El proyecto establece una base sólida para un sistema de gestión de combustible distribuido. Las tecnologías utilizadas, como Go, React y Docker, son adecuadas para este tipo de arquitectura. Sin embargo, es crucial abordar las debilidades identificadas, especialmente en lo que respecta a la seguridad y la implementación completa de la lógica de negocio en el backend de la empresa. La comunicación a través de sockets y API REST ha demostrado ser efectiva para los propósitos del sistema, pero se recomienda implementar mecanismos de autenticación y cifrado en futuras iteraciones.
